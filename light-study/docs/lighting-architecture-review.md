# 夜景 6.23 ms 后的架构判断

本轮是基于用户实机截图、当前代码和已捕获 WGSL 的架构审查；未实施下一版 shader，也没有宣称新的性能收益。

## 实机证据

用户 Chrome 截图：WebGPU / lovelace，2406×1309 drawing buffer、DPR1，静态遮挡图集路径，117156 三角面、19 批、48 draws / 8 passes。

| 通道 | GPU ms |
| --- | ---: |
| 主照明与阴影 | 4.85 |
| 几何法线 | 0.66 |
| AO 三个通道合计 | 0.53 |
| 光晕两通道合计 | 0.14 |
| 最终输出 | 0.07 |
| 总计（独立时间戳，存在显示舍入） | 6.23 |

主通道占约 78%。不能由此直接确定 4.85 ms 内算术、纹理、overdraw、MSAA/HDR 带宽各占多少。也不能将不同截图机位/分辨率的 16.45 与 6.23 ms 当成严格的同条件 A/B。

## 已确认的结构问题

1. `artifacts/static-shadow-final/cached-shaders/41.wgsl` 是实际输出照明与 emissive 的石材主通道。三盏灯的距离衰减、漫反射与 GGX 分别展开；距离衰减为零后仍继续 BRDF 求值，没有灯光空间列表或整个灯计算的零贡献跳过。阴影图集消除了 PCSS，但没有改变全灯列表求值方式。当前只有三灯；增加大量灯会继续扩大每个片元的灯光求值。
2. `src/streetLighting.ts` 白天仅将点灯强度置零，没有昼夜材质/灯光变体；零强度仍是运行时 uniform。不能假设编译器会把整个点灯路径常量折叠掉。
3. 主照明和 emissive 使用两个全分辨率 half-float 颜色附件、4× MSAA，另有法线/深度几何 pass。法线 pass 已实测 0.66 ms；主 pass 的 MSAA、颜色附件和 resolve 成本尚未单独测量。MSAA 不等于对所有像素运行四次完整片元 shader，不能用这种错误解释归因。
4. 当前遮挡图集 RGB 固定对应三灯，适合本次固定街景验证，不是大量静态灯和动态角色的通用阴影架构。每增加三灯就新增一张同规模图集不具备合理扩展性。
5. `src/streetModel.ts` 按材质/灯具归属将整街合成大网格。大场景需改为空间块内合批，维持普通几何常驻，通过视锥控制实际绘制；不能以角色距离卸载场景替代这项设计。

生成代码中的重复表达式不必然等于最终 GPU ISA 中的重复工作，不能拿 WGSL 字符数或临时变量数量当性能结论。上述无贡献灯光求值属于需实测的明确候选，而不是声称已经解释了全部 4.85 ms。

## 建议重构范围

保留 Three 的场景、资产加载和 WebGPU 资源管理，重构灯光组织、材质求值和 pass 组织。先验证三灯路径的有效贡献跳过与 pass 成本；增加灯数时对比 Forward+/clustered：对屏幕/视空间分区构建影响灯列表，每个表面只计算相关灯。分区只筛灯，不删除远处普通物体。太阳单独处理；静态场景与动态角色的阴影职责明确区分。

2026-10-20 skill 源码调研补充：r186 已提供 `DynamicLighting` 和 `ClusteredLighting`，后者也有 BRDF 前的距离检查，应优先研究复用，不能假定需要从零写分区系统。不过两者均不批处理 `castShadow=true` 的灯，而当前三灯的静态可见度通过 `shadowNode` 注入；直接切换 lighting 不会优化这三灯，关闭投影又会绕过现有可见度。所需工作是验证灯循环与可见度的接合，并确认少灯场景中 compute/列表固定成本是否合算。相关 skill 作者也报告过 clustered 在 headless 下获益、可见窗口中无益而撤回的结果；不据此承诺本项目收益。完整来源与限制见 [threejs-skills-research.md](threejs-skills-research.md)。

材质 shader 只保留本项目实际使用的材质功能，按材质/昼夜生成合理变体。共享每像素的法线、视线、粗糙度与 BRDF 公共项；在适用的灯光范围与有效贡献检查之后求值灯影和 BRDF。灯数据进入结构化 buffer，避免每新增一灯都展开一整段 shader。法线贴图造成的朝向需考虑，不能用不保守的几何背面判断删掉仍有贡献的光。

环境光、粗糙度/法线贴图、HDR/MSAA 与 emissive 输出分别做消融诊断。根据同机数据决定是否更换环境采样表示、合并材质贴图、压缩输出附件或调整 pass；先保留当前视觉参考。移除诊断功能不等于接受该视觉结果，不能用关闭高光/环境或降分辨率作为重构成功的证据。

Deferred 同样有额外 G-buffer 写读和抗锯齿成本；当前只有三盏灯，不能未经对照就保证它比 Forward+ 更快。先以可测原型决定最终路径，避免先完整替换引擎再寻找收益。

## 验收方式

- 固定用户当前 2406×1309 / DPR1 条件，同时记录灯数、可见灯数、像素灯列表分布、draws、各 pass 与总 GPU 时间。
- 同一机位、光色、材质、阴影柔度，先比较现有路径与新路径的三灯成本。大场景架构不能仅在多灯压力下划算，却使当前场景更贵。
- 分开增加几何、全场灯数、同屏影响灯数；构造 3/12/30 灯及空间分散/高度重叠两组测试，观察斜率，不根据一帧 extrapolate 出 30 ms。
- 保持资源常驻；验证视锥变化、角色移动遮挡、昼夜、灯具显隐以及 shader/buffer 更新，不把固定街景缓存当作动态游戏验证。
- 重构必须先发布公开入口再验证画面/交互。软件 GPU 用于功能和方向验证，最终预算由同一实机验证。

场景面积扩大不会自动让片元成本同比增加：分辨率固定时，主成本受可见几何、覆盖重叠、影响灯数和每像素工作量共同决定。当前缺少局部灯列表的设计确实存在灯数扩展风险，需要在继续扩建前处理。

## L12 实施进展

已按消融结果专门化 PMREM 环境采样、调整 AO 辅助缓冲并移除白天零强度点灯计算，保留主画面 4× MSAA 与原资产/灯影。范围分支原型未测出收益而撤回，未因此引入 clustered 的固定成本。详见 [street-optimization.md](street-optimization.md)。上述多灯空间列表、分块组织和动态角色遮挡仍是扩建前的验证事项，不因当前三灯成本改善而视为完成。
