# V32 — 加载对照试验

按用户要求先提交此前工作，基线为 `61327bd`，随后进行以下试验。测试均在已发布的 Mining 测试版公开入口进行；正式 Mining 未覆盖。

## 保留：按模型分批上传纹理

此前每张纹理都单独 initTexture、flush、创建 fence 并每 8ms 轮询完成。现在将同一已解码模型的纹理按最多 4 张、最多 4 MiB 压缩 mip 数据分批；每批统一 flush/fence，完成后才继续下一批或模型。实际当前最大批次为 458,832 字节。

仍只有一个模型解码和一个纹理转码 worker，不预先并发解码全部模型。单张纹理超过预算会明确报错。批次中不重复上传同一 Texture 对象；共享 ORM 的实际通道保留。取消和 GPU 错误时释放同步对象。

公开 Chromium + SwiftShader、960×540，每组 3 次独立冷启动，记录 CPU profile、长任务、资源与 GPU 同步调用。结果中位数：

| 指标 | 基线 | 分批上传 |
| --- | ---: | ---: |
| 上传等待次数 | 206 | 76 |
| 上传 fence 生命周期累计 | 1.761s | 0.668s |
| 表层资源准备 | 4.306s | 3.052s |
| 首次可玩 | 8.956s | 7.680s |
| 全过程最长主线程任务 | 311ms | 383ms |

最长任务并未改善：采样定位仍在同步场景组装、地下层生成或 shader 预热阶段；不能将本轮说成加载已经不卡。未发现超过 4ms 的单次纹理上传 WebGL 调用，但这不等同于硬件 GPU 传输时间。

两组的模型列表、三角数、实例数、贴图清单、GPU 资源计数完全一致，编码 mip 数据均为 26,263,584 字节。此数据是资源有效载荷，不是浏览器进程峰值内存，也不是用户 PC / 手机性能保证。

证据：`artifacts/upload-batch-audit/before-{1,2,3}/`、`after-{1,2,3}/`；汇总 `summary.json` 由 `tools/summarize-upload-audit.cjs` 生成并校验资源一致性。

## 未保留：预热任务按 4ms 预算让出

试验减少共享 shader 对象之间的定时器次数，新程序仍单独让出。三次首次可玩分别 11.481s、11.458s、7.979s，未获得稳定改善；未修改的下载、解析、场景生成也有明显耗时波动，无法把变化单独归因于此方案。

已撤回并重新发布原先的逐对象预热方式。试验 patch 和原始报告保留在 `artifacts/upload-batch-audit/reverted-warmup-budget.patch`、`budget-{1,2,3}/`，不计入已实现优化。

## 另一个只读试验

对当前主 JS（4,343,095 字节）离线压缩：gzip 为 1,347,238 字节，Brotli 为 1,151,091 字节。没有修改公共服务器缓存/压缩配置，这不是已经实现的下载收益。模型 `.part` 已使用 gzip，不能照这个比例估算整包收益；解压后的 JS 解析量也不会随传输压缩减少。

## 验证

12 项贴图内存/释放、上传批次预算、批次不重叠、取消、GPU 失败和 shader 预热回归通过。两组正式对照共六次公开启动无页面/shader 错误；资源预算断言通过。

最终保留版本重新发布到 Mining 测试版，公开运行、昼夜切换、深层传送和返回地表回归通过，无页面/shader 错误。产物位于 `artifacts/upload-batch-final/`；本轮没有视觉改动，因此该回归跳过截图。本次测试改动尚未追加提交。
