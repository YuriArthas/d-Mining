# 场景 Draft：主题封装、十层矿区与三十种资源

状态：**设计基线，首版已实施**。2026-10-03 按讨论整理，随后用户授权制作；本页保留设计方案，实际交付和验证见 [S1 实现记录](phase-scene-themes.md)。

## 1. 已确认的方向

- 明亮、块面清晰的卡通矿场，接近 Roblox 模拟器的场景感觉；矿洞里能看清地面、目标矿物和出口。
- 约十个主题，主题可以独立封装，不把具体深度写进主题或地形算法。
- 矿物约为主题数量的两到三倍；首版按 **30 种可采集资源**规划，包含 10 种基础岩土和 20 种矿物。矿物可以跨层；10 种主题基础方块分别只在所属楼层生成。
- 主题覆盖休整房间和实际开采区域，地形的主体岩石也是可采集资源，不只给营地换装饰。
- 沿用唯一程序化地形加稀疏修改；渲染与碰撞分别合并、分别加载卸载。
- 仅横屏，手机和电脑均支持；常态约 16ms/帧，偶发长帧需要明确原因。
- 本阶段先做场景。主角、动作、镐子和背包模型继续占位；整套 UI 美术另行推进。

以下具体主题名称、资源名称、配色、分布及阶段拆分为首版工作方案，可以在制作前后调整，具体实现状态以上述 S1 记录为准。

## 2. 配置和职责

| 模块 | 内容 | 不拥有的内容 |
| --- | --- | --- |
| 主题定义 | 稳定 themeId、环境色、岩壁表现规则、装饰组合、售卖/升级设施外观 | 深度、解锁条件、矿物血量/价格 |
| 资源定义 | 稳定 resourceId、名称、基础外观引用、HP、单件容量、售价和掉落物品引用 | 出现深度、房间、Three.js 实例 |
| 楼层表 | 稳定 layerId、起始深度、themeId、基础资源、矿物权重、房间/设施配置 | 材质和模型的具体实现 |
| 地形生成 | 根据坐标、种子和楼层配置产生逻辑方块，应用稀疏挖改 | 背包、售卖、主题装饰实例 |
| 场景表现 | 读取主题和方块信息，构建材质、装饰及视觉氛围 | 修改掉落、矿物属性和解锁进度 |
| 游戏应用层 | 将开采、掉落、背包、售卖、解锁和传送接在一起 | 在背包 API 内添加挖矿准入限制 |

楼层表是深度的唯一配置来源。房间高度位置、解锁阈值、传送落点、层名和主题切换均由它派生，不另写一份 400/800 等常量。房间逻辑与主题表现通过 layerId/themeId 关联，不相互调用内部实现。

示意：某楼层配置为 `id: frozen, from: 2000, theme: frozen_cave, base: ice_rock, ores: [...]`。把 from 改为 2400，该层房间和解锁阈值随之改变；主题资源本身不修改。下一层的起点决定本层终点，最后一层结束于世界底部。深度按整格对齐。

矿物分布放在楼层表：同一主题可以重复用于不同深度，并搭配不同矿物组合；主题包不强制某种矿必须出现。

这里的调整作用于新生成的一局，不实现运行中搬迁矿层。未来存档需要记录生成版本；稳定资源/楼层 ID 不随排序或深度变化而改变，本阶段不增加存档迁移系统。

### 当前代码需要整理的地方

- `terrain/strata.ts` 当前把层名、深度和分布放在一起；拆出主题引用及统一楼层配置。
- `world/rooms.ts` 当前另写了两个房间深度；改为读取楼层表派生房间、服务点和落点。
- `terrain/minerals.ts` 与 `application/items.ts` 目前重复维护部分名称和颜色；资源元数据建立一个来源，表现引用资源 ID，底层背包继续只接收注入的查询 API。
- 当前数字 kind 同时参与逻辑资源识别与图集索引。扩展时显式建立映射，不能继续依赖数组顺序等于资源身份。
- 已有 `ore.stone`、`ore.deep_stone`、`ore.coal`、`ore.copper`、`ore.gold`、`ore.crystal` 六个物品 ID 保留。固定地面当前 kind=7，不可因添加矿物而变成资源；保持非采集类别。
- 主线程与 Worker 使用同一份不可变的生成配置，主题资源加载状态不能改变逻辑采样结果。

普通矿物允许跨层复用；主题基础方块与楼层一对一绑定，不在其他层的矿物池中混入。移动楼层深度时，其基础方块生效区间随楼层边界移动，不在资源定义里硬编码深度。

### 数值和物品边界

- 每个资源独立配置 HP、体积、售价，同一资源跨层出现时这些属性不变。
- 现有六种资源的属性先保留，其余使用可运行的临时值；本草案不声称十层成长数值已平衡。
- 后续数值继续遵循此前确认的总体成长关系：售价增长比 HP 更陡，HP 增长比背包体积更陡；不把主题序号直接代入所有属性。
- 背包 add 不按容量拒绝加入；挖矿每次攻击前判断满包，已销毁资源始终完整入包。新增矿物不改变这条规则。
- 深层资源临时 HP 需配合现有镐子力量/攻速做开采耗时检查，不因增加内容而出现实际无法推进的层；完整经济平衡另行安排。

## 5. 房间、入口与设施

- 地表沿用出生区，地下在各主题起点设局部休整房间，首版共九处地下房间。
- 房间约 20×20 格、高 10 格，中心上下对齐。地板中央 8×8 格可开采，入口外一格厚表皮固定，穿过后可以自由向周围挖掘。
- 房间墙和顶部继续可开采，不因主题装饰变成新的不可挖外壳；房间外不产生横贯世界的保护层。
- 到达相应深度就解锁，无须实际进入房间。家中传送落在固定地板、入口之外，仍需附近碰撞就绪才能落地。
- 首版建议每处均可售卖；升级设施暂设在 800/1600/2400/3200/3600 米各层。这些是楼层服务配置，不是主题特性。现有手动升级 UI 保留。
- 地表设施布局单独设计；地下可复用共同的入口、落点和服务圈布局，通过墙边及上方的装饰形成主题差异。
- 每层优先一个明显的大型标志物，再配少量装饰。通路、入口和传送落点保持开阔，大物件不侵占主要相机活动空间。
- 售卖和升级设施保持一致的识别标记，外壳可以换主题；售卖踩圈执行，商店踩入打开、离开关闭。
- 首版建议巨型蘑菇、骨架、晶簇、机械装置为不可采集的场景装饰，不伪装成可选中的矿块。可采资源仍以矿体方块呈现。
- 熔岩、冰面、机械只表达主题，本阶段不加入灼伤、打滑、机关或新解谜规则。抵达底部不自动新增通关流程。

## 6. 渲染、合并和资源加载

- 主题影响岩壁和矿块表现。先通过不同基础资源形成大面积差异；必要时给某个资源增加主题外观变体，不强制制作 10×30 套材质。
- 同一种矿保留主要矿斑颜色和形状，允许底岩适配主题；外观变体不增加背包物品种类。
- 渲染合并键使用最终表面外观及朝向。主题边界有不同外观时分开合并，矿物相同也不能错误跨主题合并。
- 碰撞合并只读取实体占用，不读取主题、矿物种类、稀有度或背包属性；加载半径与渲染继续独立。
- 图集索引与稳定资源 ID 分开。尽量共享图集和材质，避免每个资源一个 draw call；不为每个矿块创建 Mesh 或装饰实例。
- 基础岩体保持连续，矿物按单格独立随机；按真实材质合并暴露面，不以矿簇代替单格分布。三十种资源是全世界总量，不代表附近要同时铺满三十种。
- 氛围色按玩家所在区域平滑调整；矿块外观由其坐标与配置决定，不能只按玩家当前主题给整个已加载矿区统一换皮。
- 场景装饰按距离创建/释放，复用几何和材质。共用资源与实例分别管理生命周期，离开一层不能释放其他层还在用的共用资源。
- 灯具主要用材质和局部亮色表达；首版控制实时灯光、阴影和透明叠加。冰岩与晶体不依赖大面积透明材质。
- 矿坑逻辑仍为坐标生成和稀疏修改，不创建密集 16³ 状态或整张世界数组。
- 性能验证关注附近表面碎片数、draw call、构建/上传耗时及内存。30 种资源不直接等于 30 倍渲染开销，但需用实际混合场景验证。

## 7. 实施顺序和难度（百分制）

这是新增场景阶段 S1，安排在现有 P3F 之后、宠物之前。下列分数为实现复杂度估计，不是工期或完成率。

| 阶段 | 工作 | 完成标准 | 难度 |
| --- | --- | --- | --- |
| S1.1 配置拆分 | 主题、资源、楼层职责分开，房间/解锁/传送统一取深度，图集与资源 ID 解耦 | 调整一层深度后各入口/设施/解锁同步；现有玩法与独立合并无回退 | 50/100 |
| S1.2 内容配置 | 填入十层和三十种资源，配置基础岩体与矿物池，接入掉落和临时属性 | 三十种资源均有身份、表现和有效用途，主线程/Worker 生成一致，采集售卖正确 | 45/100 |
| S1.3 地表与老矿井样板 | 地表设施、入口围边、老矿井支架与灯具、首版岩矿纹理 | 双端可辨认、矿块与装饰边界明确、相机/移动不受干扰，人工看效果 | 60/100 |
| S1.4 水晶主题样板 | 明显不同的晶体环境，验证外观变体与主题交界 | 能验证主题复用、加载卸载及边界合并，地下可读性稳定 | 50/100 |
| S1.5 扩展其余主题 | 按统一设施和装饰约定完成其余七个主题 | 每层有标志物，开采区与营地风格一致，传送往返资源稳定 | 60/100 |
| S1.6 性能与体验复核 | 连挖、落层、传送、镜头贴墙、各种矿物混合、装饰加载 | 双端功能和画面检查完成；目标手机单独验证帧时间和长帧原因 | 65/100 |

先完成配置及内容定义，再逐层完善美术。样板层决定后续统一画风；不先制作十套完整模型再验证镜头和手机成本。总体难度约 **65/100**，主要风险是场景质量、相机空间和手机性能，而非数据量本身。

## 8. 验证范围

- 配置：唯一 ID、引用有效、起始深度有序且整格对齐、矿物权重有效；十层与三十资源均被使用。
- 深度调整：修改一个起点后，地形分层、房间表皮、解锁、传送落点、层名一致变化，旧世界版本不被当成新版本复用。
- 生成：相同配置与种子在主线程/Worker 上一致，卸载重载不换矿；普通资源和固定地面类别不混淆。
- 合并：连续同外观区域能合并；多矿、主题交界正确分面；相同占用的碰撞复杂度不因资源数量增加。
- 游戏逻辑：各矿物正确显示、受伤、销毁、入包与售卖；跨层不改变同资源属性，满包规则不回退。
- 视觉与手感：桌面和紧凑手机横屏查看实际画面，确认入口、圈、矿物和装饰可读；走到设施、下挖、靠墙转镜头、穿越主题边界。
- 性能：按既定约 16ms 常态目标检查，长帧关联到具体操作及耗时；软件 WebGL 检查不能代替目标手机 60 FPS 验收。

## 9. 裁决和默认处理

目前没有必须由用户裁决才能拆配置的阻塞项。主题封装、资源数量级、地形关联方式及已有玩法边界已明确。

以下作为可调整的首版默认，不逐项请求批准：

- 十个主题包含地表；三十种资源包含基础岩土；每层先按 400 米。
- 采用上表的主题、矿物名称及幻想矿材；不要求矿物学写实。
- 所有地下房间可售卖，升级设施按第 5 节暂设。
- 场景装饰先不可采集，主题不增加特殊伤害或移动机制。
- 新资源使用临时数值，末层暂不加结局、重生或循环挖矿机制。

需要用户参与的是样板完成后的实际画风和手机手感判断。若用户对具体主题或矿物有偏好，可直接替换表中内容；无需为实现内部结构再增加裁决流程。
