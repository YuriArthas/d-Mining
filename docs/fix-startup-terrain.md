# 出生点地形准备与绘制积压修复

用户报告公开测试版停在「正在准备附近地形」。未把旧的降频截图脚本作为这次依据；使用没有 RAF 改写的电脑浏览器访问公开测试版，记录真实加载阶段并操作键盘和退出按钮。

发现两个启动耦合：

- 旧版等待所有场景模型完成才创建附近地形，地形队列仅在渲染帧内推进。公开复现中首个重场景帧仍有 58 个区域待准备，其中 8 个为碰撞区域。
- 普通渲染持续提交新帧，软件 GPU 出现绘制队列压力；角色逻辑已就绪时，点击退出仍可能因绘制积压超时。因此单凭 ready 状态不足以验证可交互。

修正：

- 出生点地形与模型加载并行，使用会让出主线程的独立启动任务准备。全部初始窗口与碰撞就绪后才将场景挂载；游戏中的采集提交仍保持原有物理步边界。
- 启动取消释放未挂载资源；Worker 错误或长时间无进展明确报错，不保留永久准备提示。
- Three.js 的逻辑更新与实际绘制提交分离。WebGL2 fence 以零超时轮询上一帧完成情况；GPU 忙时继续逻辑/输入，不排队更多绘制。模型、贴图、灯光和普通场景驻留规则未更改。
- 新诊断：terrainReadyMs、sceneAttachMs、terrainPendingAtAttach，以及实际提交/跳过的绘制帧数。

验证：14 项启动、取消、Worker 异常、GPU 同步和原有地形事务检查通过；构建和测试入口发布哈希核对通过，正式 Mining 不变。公开实测记录：`artifacts/startup-before.json`、`artifacts/startup-after.json`。最终电脑端公开检查使用未改写的 RAF：场景挂载前地形队列已清零，进入后角色落地、实际键盘移动和点击退出返回游戏列表均通过。软件渲染冷启动约 37.5 秒才观察到就绪，首次加载仍偏慢。

此次未声称资源下载和首屏绘制已变快，也不把软件 GPU 的耗时作为用户设备性能结论。
