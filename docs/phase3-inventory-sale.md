# P3A：解耦的背包、挖矿与售卖 API

状态：P3A.1–P3A.7 已实现，本地自动及浏览器检查通过；公网电脑/触控复核通过，用户简单视觉检查待完成。模块解耦优先，先跑通底层 API，再接最小表现。所有矿物每单位 1 金币，不做升级、数值平衡或实际存档读写。助手负责实现及验证，用户只简单检查画面。

## 1. 核心边界

**背包负责存东西和报告状态，挖矿负责决定满包时是否继续挖。**

- `inventory.add(items)` 接受物品批次，不检查容量，不因满包拒绝、不截断数量。当前已经超过容量也照常加入。
- `inventory.isFull()` 只返回 `used >= capacity`，不阻止任何写入。
- 挖矿流程在每次发起采集时查询 `isFull()`：已满则不挖；未满则完成整次采集，全部产物入包，允许本次结果超过容量。
- 例如 49/50 时一次挖到 8 个，得到 57/50；下一次挖矿由挖矿流程阻止。但直接调用背包 `add(8 个)` 仍得到 65/50。这两个用例都必须通过。
- 一次采集可含多个方块，产生多种、多数量物品。每格掉落一件只是当前配置，不是 API 限制。
- 背包暂用容量 50，金币初始 0；每单位物品占用 1。满包不自动传送，地表落地踩圈自动出售全部矿物。

不实现背包容量准入、checkAdd/tryAdd、预留、采集 token 或独立异步结算状态机。容量是可查询的数据，不是背包写入限制。已被接受的采集完成时，即使背包已满，也必须把实际销毁格子的全部产物加入；不能在销毁后再以满包为由拒绝结算。

## 2. 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| Inventory | 分类计数、批量增减、容量及满状态查询、快照、数据导出/初始化 | 是否允许挖矿、来源、金币、方块、Worker、因容量拒收 |
| Wallet | 金额和余额增减 | 矿物、售卖圈、挖矿 |
| 地形 | 目标查询、去重、有效删格及渲染/碰撞更新 | 背包、掉落物品、金币 |
| 掉落规则 | 将有效采集资源转换为物品批次 | 库存、容量限制、修改地形 |
| 挖矿流程 | 判断是否满包，调用地形和掉落规则，将本次产物加入背包 | 重写背包算法、网格构建或 Worker 调度 |
| 售卖流程 | 读取库存，按当前固定单价计算，扣物品、加金币，返回收据 | 圆圈、角色位置、地形任务 |
| 区域检测 | 按位置/高度/落地及滞回报告 enter/exit | 自行出售、修改库存和金币 |
| 会话组装 | 连接输入、挖矿、踩圈出售、返回地表与退出 | 把底层规则搬进场景帧循环 |
| 表现层 | 查询快照、发命令、显示结果 | 写库存和金币、复制业务权威数据 |

物品使用稳定 ID。矿种到物品的映射由掉落配置提供，背包不导入六种矿的枚举或图集数据。增加非矿物物品、改变单格产量或改用按钮出售，都不应要求修改无关模块。

采用普通函数/模块和显式参数，不要求每行建一个类。不引入通用事务框架、全局事件总线或额外调度器。逻辑/API 可在无 DOM、Three.js、真实 Worker 的环境测试；运行时适配负责对接现有场景。

## 3. 数据与 API

```ts
type ItemId = string;
type ItemBatch = readonly Readonly<{ itemId: ItemId; count: number }>[];

type InventoryDataV1 = {
  version: 1;
  capacity: number;
  items: Record<ItemId, number>;
};
```

- `items` 保存已持有的正整数数量；零数量删除键，同批次同 ID 合并。
- used、剩余容量和满状态由库存与 capacity 派生，不另存第二份权威数据。超容量是合法状态，UI 如实显示 57/50。
- `add(items)` 对符合数据契约的输入始终增加完整数量，不返回 full，不提供按来源跳过容量的开关——它本来就不检查容量。
- 数量为安全整数，输入错误属于数据契约错误；不借输入校验重新引入容量/来源限制。导入边界校验格式和数值，合法超容量数据必须无损接受。
- 快照/导出数据不能通过引用修改内部状态。纯数据导出、校验、初始化和往返测试本阶段实现，存储 I/O 后置。

| API | 语义 |
| --- | --- |
| `inventory.add(items)` | 同步加入完整批次；满包和超容量都不影响添加 |
| `inventory.remove(items)` | 同步整体扣除；数量不足明确失败，不部分扣除 |
| `inventory.isFull()` | 只查询 used >= capacity，是否采取限制由调用者决定 |
| `inventory.getSnapshot()` / `exportData()` / 初始化 | 只读查询和纯数据边界；不含采集/Worker 状态 |
| `wallet.credit(amount)` / `debit(amount)` / 查询 | 金额增减；不接收物品清单 |
| `resolveDrops(resources)` | 纯函数返回 ItemBatch；数量与方块数不必相等 |
| 挖矿入口 | 接受多目标，发起时查询满包状态；实际删格后完整入包，不再按容量拦截 |
| `sale.sellAll()` | 读库存，按 1 金币/单位扣矿加钱并返回收据；空包返回 empty |
| `zone.update(sample)` | 返回进入/离开，不调用经济 API |
| 会话查询/订阅及玩家命令 | 完整操作结束后通知 UI；UI 不获得底层写入口 |

## 4. P3A.3：多格采集接入

游戏逻辑按同步顺序组合：

```text
挖矿检查 isFull()
  → 未满：采集本次有效目标
  → 根据采集结果生成物品批次
  → inventory.add(整批产物)
  → 返回结果并更新表现
```

判断只做在本次采集前，不按每格或每种产物重复判断。已满时由挖矿流程停止，背包不参与决定。连续调用 A 导致满包后，调用 B 的挖矿检查阻止继续挖；其他来源仍可独立调用 add。

现有地形确实使用 Worker 准备网格和碰撞，但这是地形内部实现。当前 `TerrainStream.process()` 已有同步删格/切换资源的提交点；该点只报告实际销毁结果，挖矿流程直接入包。满包检查在请求入口，沿用现有地形准备/取消机制。输入到实际删格可能有等待，不等于背包或游戏结算需要 Promise、预留、业务请求 ID 或独立异步协调器。不能把所有网格计算改为同步，也不为简化接口提前删逻辑格而破坏现有碰撞一致性。

一次玩家采集可有多个目标；地形适配保留这个目标组，计算任务怎么拆都不改变一次采集的边界。每个采集请求分别在入口判断满包；已接受请求可共同计算，完成后全部入包，不因先完成的请求填满背包而丢弃其余产物。本阶段不要求新增跨采集操作的计算合批优化。

满包检查发生在挖矿请求入口。地形提交点根据实际销毁的格子产生结果，随后同步计算掉落并调用 add；完成后才通知表现层。未实际挖除不发物品，已经销毁就不再检查容量。地形的旧回复丢弃、资源释放继续留在地形内部，不传播到背包/售卖接口。

API 和集成用例实际支持多格、多种产物，包括超过现有 8 格计算批次的目标组。当前地形等待队列最多容纳 32 个有效格，超出本次剩余队列预算整体返回未接受；不部分吞入目标组。该上限属于地形工作预算，和背包容量无关。玩家暂用单格输入，不新增范围镐、爆炸或额外美术。

## 5. 售卖与最小表现

- SaleService 只处理库存、固定价格和钱包。先校验扣除/金额结果，再同步扣矿加钱，完整操作后通知 UI；N 个物品卖 N 金币，超容量库存也全部出售。
- 区域检测依据脚底位置、地表高度、grounded 和进出滞回，只报告状态变化。会话收到进入事件后调用售卖，停留不每帧重复结算。
- 售卖区内停止发起挖矿；进入或返回时停止输入并清理地形尚未提交的挖除，沿用已有运行时能力。这不是背包或售卖服务的职责。
- 返回按钮落在圈外安全位置，保留已入包物品和已提交矿坑修改，等附近碰撞可用后恢复移动；不自动出售。
- 最小画面包括真实数量/容量、分类数量、金币、售卖圈、返回按钮、满包和出售提示。只在状态变化时更新 UI。

## 6. 子阶段及百分制难度

0–100 分，越高越难，表示实现与调试复杂度，不是完成率或工期。20 为简单接线，40 为常规模块及集成，60 为较复杂状态协调，80 以上为复杂架构或高不确定性问题。实现已完成，验收记录见下节。

| 子项 | 交付 | 难度 |
| --- | --- | --- |
| P3A.1 数据和职责契约 | ItemBatch、DTO、查询/写入边界、模块依赖 | 30/100 |
| P3A.2 背包与钱包 API | 批量增减、只读满状态、快照、数据往返；add 不受容量限制 | 25/100 |
| P3A.3 多格采集接入 | 挖矿自己判断满包，多目标掉落及同步入包，接现有地形提交点 | 40/100 |
| P3A.4 售卖 API | 按件扣矿加钱、空包与收据 | 25/100 |
| P3A.5 区域及会话接线 | 踩圈售卖、返回地表、沿用退出/地形清理 | 35/100 |
| P3A.6 最小表现 | HUD、圆圈、按钮、结果提示 | 20/100 |
| P3A.7 解耦及完整验证 | 模块独测、多格集成、完整浏览器循环 | 40/100 |

整体 **40/100**。之前 70/100 的采集评估包含了不需要新增的业务异步协调机制，已删除。保留的实际工作是让现有地形入口支持完整目标组并接入同步业务逻辑，不是重写 Worker 架构。

按 P3A.1 至 P3A.7 推进，各模块测试随实现完成。P3A.4 只依赖库存与钱包契约，不需要等待地形模块才能独测。

## 7. 验证责任

助手负责：

- 背包：49/50 加 8 得 57/50，再直接加 8 得 65/50；容量 0 仍可 add；isFull 只反映状态。批量与多次 add 的最终库存一致，不带挖矿规则。
- 挖矿：49/50 时采集混合 8 件全部入包，之后不再删格或发矿；出售/扣除到未满后恢复。满包阻止发生在挖矿调用处。
- 多格：一次 12 格及重复/空目标、跨区域任务；掉落可配置为一格多件或多种物品；只按实际采集结果入账，不随 Worker 拆分改变容量判断。
- 解耦：非矿物来源可直接 add；地形可脱离背包测试，背包可脱离挖矿测试；售卖不依赖地形/区域，区域不依赖经济模块。
- 数据：超容量导出和初始化无损；快照副本不改内部状态；非法数据及扣除不足不产生部分修改。
- 售卖：空包、混合矿、超量库存、重复出售和金额边界；N 个获得 N 金币。
- 集成：新请求时已满则不发起挖矿；已经接受的请求完成时满包仍完整发矿；未提交地形取消不发矿；原有地形资源/回复处理不重复触发业务。鼠标/触控完整跑通挖矿→满包→返回→踩圈→继续挖矿。

用户只简单检查数量、金币、圆圈和按钮。常态约 16ms 和目标手机性能要求继续保留，设备验收仍单列；不以 API 测试代替实机证据。
