# RF：逐步拆分结构，再收敛关卡配置（Draft）

状态：RF0—RF7 已完成。实施与验收见 `docs/runtime-refactor-results.md`，原始基线见 `docs/runtime-refactor-baseline.md`，配置修改入口见 `docs/level-content-guide.md`。

目标：先建立清楚的职责、状态所有权和调用关系；在逐块迁移时提取输入参数，最终使布局、模型、主题、灯光容易修改。本版替代先全面配置化再拆运行时的顺序。不是把整个入口搬进一个 GameRuntime 大类。

阶段难度综合实现复杂度与回归风险，满分 100，不是失败概率。整体暂估 70/100，完成 RF0 后复核。

## 1. 当前代码依据

- ValidationScene.tsx 同时负责并行启动、订阅、环境应用、移动、相机、选格、调试、绘制和清理；预热和正常帧重复部分环境设置。
- RoomFacilities 同时持有普通场景视觉和附近碰撞，并通过 userData 转调表层效果；不是纯业务设施模块。
- loadStaticSurface 混合解码、材质处理、实例组装、批处理、地表细节及诊断；用模型名推断一些行为。
- GameSession 的业务协调职责合理，但直接导入当前地图的服务区、传送点和房间表。
- 保留 Inventory、Wallet、Mining、MiningCombat、TerrainStream、CharacterPhysics、ThirdPersonCamera 等已有边界；不为统一命名再包一层。

## 2. 对象设计原则

有持续状态、资源或生命周期的职责适合对象；计算、数据转换、确定性生成适合函数；配置保持只读数据。

- 优先组合，不引入深继承、统一 BaseSystem、ECS、依赖注入容器或通用事件总线。
- 构造阶段建立依赖；异步准备显式执行，不在构造函数里偷偷启动 RAF 或网络任务。
- 对象只接收需要的能力和数据，不传入包含全游戏的 RuntimeContext，不访问彼此私有字段。
- 不为每个具体类机械增加接口；跨业务/引擎边界、需要替代实现或测试隔离时再定义小接口。
- 先迁移现有行为，再独立调整算法或美术；文件数、类数量、行数都不是验收目标。

## 3. 拟议职责与所有权

这些是目标边界，不要求一次性新建全部类；已有对象能承担职责就复用。

| 模块/对象 | 负责 | 不负责 |
| --- | --- | --- |
| React 场景入口 | Canvas 接入、UI 回调、创建与卸载运行对象 | 具体玩法、关卡坐标 |
| 启动装配函数 | 创建对象、加载、预热、绑定业务与引擎、失败清理 | 每帧玩法、关卡内容定义 |
| EnvironmentController | 环境状态、天空/雾/实际光源应用，复用 SurfaceEnvironment 和 SceneLightingRig | 装饰灯模型、交易、加载队列 |
| SceneryView | 普通场景节点、实例与显示状态；明确引用表层效果对象 | 物理碰撞、交易、随意销毁共享资产 |
| SceneryCollision | 普通物件碰撞句柄、附近启停，借用物理世界 | 距离卸载视觉、体素碰撞、销毁物理世界 |
| ModelAssetLoader / 资产包 | 复用当前下载/解压/转码/上传流程；资产包持有共享几何、材质、纹理 | 地图摆放、业务规则 |
| 场景组装函数 | 模板、位置、材质策略转换成实例与批处理；登记新资源所有者 | 下载、帧循环 |
| 玩家运动协调对象 | 朝向、固定步进、移动输入、传送等待；调用已有物理和地形对象 | 相机算法、背包和售价 |
| 相机与采掘适配 | 复用 ThirdPersonCamera；射线选格、描边、裂痕及向 GameSession 发出操作 | 重写采矿业务、管理整个地形 |
| GameSession（保留） | 背包、战斗、出售、升级、探索等业务协调 | Three/Rapier 对象、加载场景 |
| 帧协调入口 | 明确调用顺序，连接现有调度、统计和绘制 | 各子系统内部状态、关卡特例 |
| 调试适配模块 | 通过公开查询和命令组成调试接口 | 第二套玩法、全局资源所有权 |

装配入口选择关卡并注入依赖。对象之间明确调用，不互相查找任意对象。帧协调入口保持薄；保留现有 R3F 接入和唯一 RAF，不借重构更换框架。

### 资源生命周期

1. 每个资源明确一个释放者；借用者不销毁。物理世界由会话装配层持有，碰撞模块先清理自身句柄，物理世界最后释放。
2. 共享几何/纹理由场景资产包管理，单个实例只移除自身节点。实例专属材质、批处理缓冲、程序化资源分别登记，避免现有递归销毁与新资产包重复释放。
3. 初期按整个场景生命周期释放资产包，不为尚不存在的跨场景共享需求增加引用计数框架。
4. 加载失败、取消、迟到结果均有清理路径；完成装配时明确资源从加载阶段移交到运行阶段，不由两边同时释放。
5. 退出先停止帧调用和新请求、解绑订阅，再按依赖逆序清理；异步回调不能访问已销毁对象。

## 4. 逐步实施 Phase

每阶段保留可运行版本，按小切片分别交付和公开验证，不把全部改动攒到最后。

| 阶段 | 工作与结束条件 | 难度 |
| --- | --- | ---: |
| RF0 边界与基线 | 明确调用/所有权表、帧顺序和启动清理路径；记录现状；整理即将迁移的长行，不混入行为变化 | 30/100 |
| RF1 环境对象 | 提取预热和逐帧共用的环境应用，保留所需过渡差异；灯光/天空参数由调用方传入 | 45/100 |
| RF2 场景视觉与碰撞 | 拆 RoomFacilities；视觉常驻、附近碰撞独立；不再通过隐式 userData 找表层控制对象 | 58/100 |
| RF3 资源加载与组装 | 拆 StaticSurface 的资源、材质处理、摆放/批处理；明确资产包与实例释放，保留现有并发上限 | 68/100 |
| RF4 玩家与交互 | 分步提取移动/传送协调、相机适配、采掘适配；沿用已有物理、相机、挖矿实现 | 60/100 |
| RF5 启动与帧协调 | 子职责迁出后再提取启动装配、失败清理、调试接口；入口保留明确调度顺序 | 72/100 |
| RF6 关卡配置收敛 | 汇总已形成的参数；注入 GameSession 设施/层配置；统一锚点、地下空洞/深度/传送数据；消除模型名与层名特例 | 65/100 |
| RF7 配置修改验收 | 通过配置移动设施、换外观、调照明、改地下层深度/主题，公开回归并检查性能 | 40/100 |

顺序：RF0 → RF1 → RF2 → RF3 → RF4 → RF5 → RF6 → RF7。

配置提取贯穿 RF1—RF5，每次只定义该模块当前确实需要的参数，不预先设计完整 schema。RF6 是统一和查漏，不是第一次做配置分离。

### 最小切片

- RF1：先提取环境计算与应用，再让预热与正常帧共用；装饰灯不归真实光源所有权。
- RF2：先普通碰撞管理，再视觉容器和表层效果引用。保持原有释放行为，资产包所有权迁移留在 RF3。
- RF3：先拆加载与摆放，再单独迁移共享资源释放，最后把按名字选材质改为显式策略；每步验证失败/取消路径。
- RF4：先相机适配，再选格与反馈，最后移动/传送状态，避免同时更换三条时序链；子项约 40、50、62/100。
- RF5：先启动装配与清理，再调试接口，最后收口帧协调；不将整个 effect/useFrame 原封不动搬进新大类。
- RF6：先以售卖设施验证单锚点和外观/业务分离，再推广至表层与地下；不能只移动可见房间而留下原地形空洞、碰撞和落点。

## 5. 必须保持的机制

拆分前核对现有顺序，不借重构改变模拟频率、输入消费时点或绘制策略。

- 一个 RAF 所有者，渲染限帧与固定物理步进独立。
- 普通场景碰撞和体素碰撞在对应物理步前准备；地形提交仍位于物理 step 前，不能在任意异步回调安装。
- 传送等待目的地地形就绪，再放置角色并重置相机；跳跃、视角、点击等一次性输入不能由多个对象重复消费。
- 相机矩阵更新后选格，再向业务层攻击；描边/裂痕消费结果，不承担扣血结算。
- 地形/渲染/碰撞的同步版本切换和采集回调语义不变。Inventory.add 不因满包拒收；挖前满包判断仍归采矿业务。
- 预热使用首帧所需材质/环境状态；成功提交首帧后才结束加载，进度不倒退、不在阶段间归零。
- 稀疏逻辑地形保持唯一数据源；体素渲染合并、体素碰撞合并、普通物件碰撞独立；普通视觉不按距离卸载。

## 6. 配置最终形态

使用带类型的 TypeScript 只读数据，不含 React/Three/Rapier 实例和任意执行回调，不建立编辑器、DSL 或通用配置引擎。

- 楼层：稳定 ID、深度、主题、矿物分布、房间和设施引用。
- 布局：锚点、局部偏移、实例尺寸/朝向、道路/池塘/入口范围。
- 外观：模型、材质策略、已有 shader 参数、程序化组件参数。
- 碰撞：独立形状与规格，可引用共用锚点，不由模型名推断。
- 照明：真实光源和装饰灯分别配置，显式昼夜状态。
- 设施：类型、触发范围、目的地/外观引用，不通过数组下标取模猜外观或行为。

配置校验与派生在启动/构建边界完成，不逐帧解析。世界单位明确，格数通过 CELL 换算。地下深度统一转换为场景原点；Worker 输入可序列化且与主线程生成结果一致。

未知引用、缺传送展位、无效尺寸明确报错。复用已有能力只改配置与资产；新增效果仍需实现。移动烘焙依赖的几何可能需要重新烘焙，不承诺热更新。

## 7. 验收

结构：能明确回答状态归谁、资源由谁释放、更新由谁调用；不增加万能上下文、双 RAF 或相互访问私有状态的依赖环。

内容：移动/旋转售卖设施，模型/标识/触发区/独立碰撞一致；换房子不改交易；改照明不改帧循环；调围墙/道路/草不改生成器；改地下层深度/主题后空洞、开口、解锁、传送一致。

运行：按阶段覆盖相关取消/失败/释放、昼夜、相机/选格、采集/售卖/传送；检查加载并发、总进度、资源数量与内存。不声称结构重构必然减少下载或提高帧率。

可试玩改动先发布到公开 Mining 测试入口，再做电脑场景/交互/截图验证；必要时新增公开实验入口并列入列表，不覆盖正式版、不擅自增加手机检查。维持现有美术和玩法；配置实验结束恢复约定布局，除非用户接受新布局。静态检查不替代实际画面与交互证据。
